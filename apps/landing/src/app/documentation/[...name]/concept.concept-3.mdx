# `Validated<T>` and 422

`Validated<T>` is a Vespera extractor wrapper that validates the extracted value **before** your handler is called. Invalid requests are rejected with `422 Unprocessable Entity` and a canonical JSON error envelope — no per-handler error mapping, no boilerplate.

## Basic Usage

Declare constraints with `#[schema(...)]` on a `#[derive(Schema)]` type. The derive generates the validator itself — **no extra dependency** — and the same constraints are written into the OpenAPI schema (`minLength`, `pattern`, `format`, `minimum`, …):

```toml
[dependencies]
vespera = "0.6"
```

```rust
use serde::Deserialize;
use vespera::{Schema, Validated, axum::Json};

#[derive(Deserialize, Schema)]
pub struct CreateUser {
    #[schema(min_length = 3, max_length = 32, pattern = "^[a-z0-9_]+$")]
    pub username: String,
    #[schema(format = "email")]
    pub email: String,
    #[schema(minimum = 18, maximum = 120)]
    pub age: u8,
}

#[vespera::route(post, tags = ["users"])]
pub async fn create_user(
    Validated(Json(req)): Validated<Json<CreateUser>>,
) -> Json<&'static str> {
    // `req` has already passed validation — no manual checks needed.
    Json("ok")
}
```

Validation is part of the default `validation` feature. With `default-features = false`, re-enable it with `features = ["validation"]`.

## 422 Response Envelope

When validation fails, Vespera returns `HTTP 422 Unprocessable Entity` with this JSON body:

```json
{
  "errors": [
    { "path": "username", "message": "length is lower than 3" },
    { "path": "email",    "message": "not a valid email" }
  ]
}
```

The envelope is identical regardless of which extractor failed — your API clients only need to handle one error shape.

### Deserialization failures use the same envelope

Input that is well-formed but does not deserialize into the target type — a wrong JSON type, a missing field, an unparsable query, form or path value — is also reported as `422` with this envelope, and `path` points at the offending field (for example `"age"` or `"tags[1]"`). Malformed JSON syntax (`400`), a missing or unsupported `Content-Type` (`415`) and body-limit errors keep axum's default rejection.

Every route with a `Validated` or `ValidatedWith` argument documents the `422` response in the OpenAPI spec, wherever the argument sits in the signature (for example after a plain `Path<T>`).

### The payload must implement `garde::Validate`

`#[derive(Schema)]` generates `garde::Validate` only for a struct with named fields and at least one runtime `#[schema(...)]` rule. A rule-less struct or an enum inside `Validated` fails to compile at the argument, with an error saying that the type cannot be validated by `Validated` / `ValidatedWith`. To fix it, add a rule, derive `garde::Validate` yourself, or take the plain extractor.

## Context-Aware Validation: `ValidatedWith<C, T>`

`ValidatedWith<C, T>` works like `Validated<T>`, but validates with a context `C` borrowed from the router state. Use it for garde rules declared with `#[garde(context(C))]`. The state provides the context through `vespera::ValidationContext<C>`. A state of type `C` implements it automatically. App state can expose a field without cloning it per request:

```rust
use std::sync::Arc;
use vespera::{Schema, ValidatedWith, ValidationContext, axum::Json};

pub struct TagPolicy {
    pub required_prefix: String,
}

pub struct AppState {
    pub tag_policy: TagPolicy,
}

impl ValidationContext<TagPolicy> for Arc<AppState> {
    fn validation_context(&self) -> &TagPolicy {
        &self.tag_policy
    }
}

#[derive(serde::Deserialize, Schema, garde::Validate)]
#[garde(context(TagPolicy as policy))]
pub struct TaggedPost {
    #[garde(custom(|tags: &Vec<String>, policy: &TagPolicy| {
        if tags.iter().all(|t| t.starts_with(&policy.required_prefix)) {
            Ok(())
        } else {
            Err(garde::Error::new("bad tag prefix"))
        }
    }))]
    pub tags: Vec<String>,
}

#[vespera::route(post)]
pub async fn create_post(post: ValidatedWith<TagPolicy, Json<TaggedPost>>) -> &'static str {
    let Json(_post) = post.into_inner();
    "ok"
}
```

`ValidatedWith` wraps the same extractors as `Validated` and answers the same `422` envelope. The spec documents the wrapped body or query parameters plus the `422` response. The context never appears in the spec. Its second field is private, so take the argument by name and use `into_inner()`, `get()` or `Deref`.

## JNI Hoisting

Under JNI, the same `422` body is **hoisted** into the binary wire header as `"validation_errors": [...]`. Java decoders can read validation errors directly from the header without parsing the response body — no special-casing needed on the Java side.

```json
{
  "v": 1,
  "status": 422,
  "headers": { "content-type": "application/json" },
  "validation_errors": [
    { "path": "username", "message": "length is lower than 3" }
  ]
}
```

## Alternative: Using `garde` Directly

For rules `#[schema(...)]` does not cover (custom validators, validation contexts, `inner(...)` rules), derive [`garde`](https://docs.rs/garde)'s `Validate` yourself. `Validated<T>` is built against **garde 0.23**, so add exactly that version:

```toml
[dependencies]
vespera = "0.6"
garde = { version = "0.23", features = ["derive", "email", "url"] }
```

```rust
use garde::Validate;
use serde::Deserialize;
use vespera::Schema;

#[derive(Deserialize, Schema, Validate)]
pub struct UpdateProfile {
    #[garde(length(min = 1, max = 100))]
    pub display_name: String,

    #[garde(url)]
    pub website: Option<String>,

    #[garde(length(min = 8))]
    pub password: String,

    #[garde(range(min = 0.0, max = 5.0))]
    pub rating: f64,

    #[garde(inner(length(min = 1)))]
    pub tags: Vec<String>,
}
```

Use one approach per type: runtime `#[schema(...)]` constraints and `#[derive(garde::Validate)]` on the same struct both implement `garde::Validate` and fail to compile (`E0119`).

`#[derive(Schema)]` documents every `#[garde(...)]` rule that has an exact JSON Schema equivalent, on object properties and on `Query<T>` / `Path<T>` struct parameters, so the spec states what the `422` enforces:

| `#[garde(...)]` rule | OpenAPI |
|---|---|
| `length(chars, min, max)` on a string | `minLength` / `maxLength` |
| `length(min, max)` on a string in the default `simple` (byte) mode, or `bytes` / `graphemes` / `utf16` | only `min = 1` becomes `minLength: 1`. JSON Schema counts code points, so other bounds are skipped |
| `length(min, max)` on a `Vec` / set / map | `minItems` / `maxItems`, `minProperties` / `maxProperties` |
| `range(min, max)` / `range(equal)` with numeric literals | `minimum` / `maximum` |
| `email` / `url` / `ipv4` / `ipv6` / `ip` | `format: email` / `uri` / `ipv4` / `ipv6`, `ip` as an `anyOf` of both |
| `pattern("...")` / `prefix("x")` / `suffix("x")` / `contains("x")` / `ascii` | `pattern` (literals escaped, extra patterns in `allOf`) |
| `inner(...)` on `Vec<T>` / `[T; N]` (on `Option<T>`: the value) | the rules on `items` |

Rules on an `Option<T>` field constrain the non-null value. A keyword set by the field's `#[schema(...)]` wins, and bounds implied by the type (`u32` gives `minimum: 0`) are only tightened. These rules are not documented because they have no exact equivalent: `alphanumeric` (Unicode classes), `required` (the same component documents responses), `credit_card`, `phone_number`, `matches`, `custom`, `dive`, `if`, non-literal arguments (consts, static regexes), and byte / grapheme / UTF-16 length bounds above 1. Use `length(chars, ...)` when the bound should appear in the spec.

See the [garde documentation](https://docs.rs/garde) for the full list of available constraints.
