# Migrating to 0.6

The 0.6 release (unreleased) is a hardening pass: OpenAPI output becomes more faithful to what serde actually serializes, `Validated<T>` reports deserialization errors through the `422` envelope, and the in-process / JNI transport gets default resource limits. This page lists every change that can affect an existing 0.5 application.

## OpenAPI Output

- **Untagged enums** emit `anyOf` (previously `oneOf`).
- **Tuple / newtype structs, fixed-size arrays and tuples** get real `array` / inner schemas instead of a generic object.
- **`skip_serializing` / `skip_serializing_if` fields** are no longer `required`.
- **Tagged newtype variants**, variant-level `skip` / `other`, and `Arc` / `Rc` / `Cow` / `NonZero*` wrappers are supported.
- **Plain tuple returns** (e.g. `(StatusCode, Json<T>)`) and body-less `error_status` codes are documented.
- **Colliding default `operationId`s** are module-qualified. Two explicit, identical `operation_id = "..."` values are now a compile error.
- **Known `headers::*` `TypedHeader` parameters** use the real HTTP header name.

### New compile errors

Code that previously compiled with a silently wrong spec now fails at compile time:

- an unknown security scheme referenced by `security = [...]` (checked after `merge`),
- a malformed `#[schema(...)]` attribute,
- an internally tagged enum (`#[serde(tag = "...")]`) with a scalar newtype payload,
- duplicate explicit `operation_id`s.

## `Validated<T>` Deserialization Errors

`Validated<Json<T>>`, `Validated<Form<T>>`, `Validated<Query<T>>` and `Validated<Path<T>>` now turn **deserialization failures** (wrong type, missing field, unparsable value) into `422 Unprocessable Entity` with the same `{"errors":[{"path","message"}]}` envelope as rule violations. Previously these returned axum's plain-text rejections (`422` / `400`). Malformed JSON syntax (`400`) and `415` content-type errors are unchanged. See [Validated & 422](/documentation/concept/concept-3).

## In-Process / JNI Limits

Set a limit to `0` to disable it. Outside Spring, use the `vespera.limits.*` / `vespera.async.*` / `vespera.runtime.*` system properties, the matching `VESPERA_*` environment variables, or the Rust-side setters in `vespera::inprocess` (for example `set_max_request_bytes`).

Streaming dispatch also changed:

- `dispatchStreaming` / `dispatchFullStreaming` throw `IOException` when the response fails **after** body bytes were written (previously a synthetic `500` header after a partial body).
- `dispatchStreaming` hoists `422` `validation_errors` into the wire header like the buffered modes.

## Java Bridge (`vespera-bridge`)

1. **Spring is a provided dependency.** The bridge no longer exports `spring-boot-starter-web` / `jackson-databind`; declare them in your app if you relied on them transitively. Spring Boot 3.5 and 4 are supported.
2. **`HEAD` keeps the real `Content-Length`** of the matching `GET` instead of `Content-Length: 0`.
3. **Native library extraction** is per-user, permission-checked and content-addressed (`vespera-native-<sha256-prefix>/` under `vespera.native.dir` / `VESPERA_NATIVE_DIR` / `<java.io.tmpdir>/vespera-<user.name>`) and reused across restarts.
4. **Autoconfiguration** is an `@AutoConfiguration` that also requires Spring MVC and the servlet API on the classpath.
5. **The new `configure*` methods return `boolean`** (`false` when the native side already fixed the value). `configureStreaming(int, int)` keeps its `void` signature.
6. **Upgrade the JAR and the native library together.** A new bridge JAR paired with a cdylib built against an older `vespera` crate binds the `configure*0` JNI hooks to the wrong signatures — rebuild the Rust library whenever you upgrade `vespera-bridge`.

7. **Oversized buffered responses answer `500`, not `413`.** `vespera.bridge.max-buffered-response-bytes` (default 64 MiB) is forwarded to the native buffered-response cap unless `vespera.bridge.native.max-buffered-response-bytes` (or its sysprop/env) sets it.
8. **CORS preflights reach Rust by default.** `vespera.bridge.cors=rust` routes `OPTIONS` preflights to the Rust router (configure a `tower_http` `CorsLayer` there); set `vespera.bridge.cors=spring` to keep Spring MVC's CORS handling.
9. **Proxy errors are generic.** Unexpected failures answer `vespera dispatch failed` (details in the WARN log with the request id); a missing native library answers `503`.
10. **Bounded app names.** `DispatchEvent.app()` and the `app` metric tag report `UNKNOWN` for client-selected app names not known to be registered.
11. **Version check.** `VesperaBridge.init` fails when the native library's `major.minor` differs from the bridge's; `-Dvespera.native.versionCheck=warn` or `off` relaxes it.

The Gradle plugin's `publishPlugins` task now fails without Plugin Portal credentials. A hyphenated `crateName` now works (new optional `packageName` / `libName`), `bridgeVersion` defaults to the matching bridge release, and `cargoSourceRoots` is ignored.
